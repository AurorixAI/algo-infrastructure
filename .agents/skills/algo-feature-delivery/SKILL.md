# ALGO: от потребности до проверенной фичи

Навык поддерживает работу в ALGO: несколько отдельных Git-репозиториев образуют один продукт. Корень репозитория, содержащего этот навык, — `algo-infrastructure`; соседние сервисы разрешать относительно его родителя, а не фиксированного пути на машине.

## Прежде чем менять

Прочитать относящийся к запросу этап [рабочего плана](../../../docs/engineering/ROADMAP.md) и [выполненное с ограничениями](../../../docs/engineering/IMPLEMENTED_AND_LIMITS.md). Аудит, написанный тест, локальный кандидат и опубликованный релиз — разные состояния. Не объявлять запланированное исправление уже работающим.

Сформулировать кратко: кто сталкивается с проблемой; конкретный исходный сценарий; что человек должен суметь сделать после изменения; как проверяется результат. Если владелец предложил механизм, проверить его влияние на эту потребность и назвать существенный компромисс. Разрешать обычные технические решения самостоятельно; вопрос нужен, когда разные варианты меняют продуктовую цель или полномочия.

До реализации проследить путь через [карту кодовой базы](references/codebase-map.md): UI → API → право доступа → данные/очередь → производные документы и другие потребители. Читать только затронутые участки. Для каждого изменяемого состояния выяснить источник истины, допустимые переходы и поведение при повторе, refresh и сбое. Проверить соседний сценарий той же функции: teacher/admin/student, другая группа, чужая попытка, старый результат, пустой и безошибочный результат — по применимости, без расширения задачи на весь продукт.

## Реализация и последствия

- Исправлять источник причины и всех затронутых потребителей. Не маскировать ошибочный уровень текстом отчёта или CSS.
- Для выданных заданий, опубликованных экзаменов и завершённых попыток сохранять исходные версии условий, вариантов, ключей и итогов. Ревизия отчёта различима с исходником; неизвестный старый snapshot не восстанавливать вымышленными данными. Изменение банка не должно незаметно переписывать историю.
- Сохранять границы доступа центра/группы и разделение организационного решения администратора, предметного вывода и автоматического текста. Новое действие должно иметь понятного автора и время, если меняет состояние ученика или публикации.
- `question_latex` — канонический заполненный источник условия; `question_text` используется при его отсутствии. Выбор по длине не возвращать. Решённое отображение LaTeX не переоткрывать без конкретной новой ошибки в текущем объёме.
- Намеренные деактивации заданий и неподтверждённых рисунков сохранять. Восстанавливать доступность по проверенному содержательному основанию в авторизованной задаче.

## Проверить результат, а не сходство с кодом

Для изменения бизнес-логики добавить содержательную регрессию: воспроизвести исходный дефект на наблюдаемом контракте и проверить правильный результат. Не подменять тестируемое решение mock-результатом этой же функции. Изолировать внешние границы; блокировки, транзакции и гонки проверять на PostgreSQL/Redis, если именно они обеспечивают исправление. SQLite-проверка сортировки не доказывает PostgreSQL-конкурентность.

Выбрать остальные проверки по влиянию: контракт связанных сервисов; восстановление после ошибки; production-сборка; реальный браузер и границы клика/контента при UI-изменении; web/PDF/ключ при изменении задания. Самостоятельное математическое решение и QA-прохождение по серверным ключам помечать раздельно. Платные модели выключать в обычной приёмке; оплачиваемый прогон требует отдельной авторизации затрат.

Для небольшой правки копии или обратимого оформления достаточно релевантной проверки; не создавать тест, повторяющий новый текст. После успешных обязательных проверок повторять их только при новых изменениях, сбоях или нерешённом риске.

## Закрытие работы

Зафиксировать: потребность и новый сценарий, причину, изменённые контракты/версии, доказательства, ограничение результата и оставшийся этап. Успешные синтетические профили не объявлять эмпирической точностью на школьниках. Обновить один основной план без конкурирующих очередей.

Коммит, push и публикацию выполнять в предоставленном владельцем объёме через [Git-release workflow](../algo-git-release/SKILL.md). Разрешение на stage не является разрешением на production. Если публикация ещё не разрешена, сначала подготовить конкретный проверенный кандидат, затем запросить разрешение на его выпуск.
