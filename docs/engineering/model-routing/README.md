Явный чек-лист исправляет известные провалы, но не защищает от неизвестных. Haiku тратит больше токенов и времени, поэтому выигрыш в цене меньше разницы в цене за токен.

## Роли

| Модель | Делает | Не делает |
|---|---|---|
| **Opus** (ведущий) | план и декомпозиция, промпты и чек-листы для исполнителей, решения, мини-R3 правок, приёмка, выкладки, отчёт владельцу | массовую работу |
| **Sonnet** (заместитель) | исполнение волн контента (проверка + написание объяснений), код, сборщики, **R3-ревью** (независимое), выборочная проверка работы Haiku, всё 10–11 класса, доказательства, системы, комплексные числа | финальных решений по ключам и выкладке |
| **Haiku** (исполнитель первого прохода) | массовый первичный проход по строгому чек-листу: сортировка/классификация дефектов по банку, первичная проверка объяснений 5–9 кл., нормализация записи и LaTeX, черновики объяснений | не пишет в БД; не является последней проверкой; не меняет ключи |

## Правила потока

1. Промпт для Haiku — всегда с явным чек-листом проверок (как `bench/round2_prompt_strict.txt`) и форматом вывода JSON.
2. Любой результат Haiku проходит: (а) детерминированные проверки скриптом (sympy-вычисление значения, KaTeX, баланс `$`, различимость вариантов, ключ не тронут); (б) Sonnet: всё помеченное + случайная выборка не меньше 20 % (на старте — 100 %, пока доля расхождений не станет < 2 % на двух волнах подряд).
3. Перед записью в БД — как раньше: R3 (Sonnet, независимо) → мини-R3 ведущего для правок после R3 → бэкап → запись.
4. Эскалация: Haiku «не уверен» или расхождение со скриптом → Sonnet; смена ключа, спорная математика, решение по продукту → Opus/владелец.
5. Регрессия: при обновлении моделей прогнать `bench/` и сравнить с `bench/result_*.json`.

## Файлы
- `bench/round1_prompt.txt`, `bench/round2_prompt.txt`, `bench/round2_prompt_strict.txt` — промпты (одинаковые для всех моделей).
- `bench/round{1,2}_key.json` — эталон.
