# Diagnostic-service: проверка перед фиксацией stage-кандидата

Дата: 04.10.2026, Asia/Tashkent. Проверены все незакоммиченные runtime-изменения, тесты, `docs/diagnostic-lifecycle.md` и существующий deploy workflow. Код, банк, stage, Git index и ветки не изменялись. Новые работы N01–N12 не выполнялись, платные модели не вызывались.

**Вывод:** новых блокирующих дефектов, мешающих сохранить уже опубликованный кандидат в Git, не обнаружено. Это разрешает фиксацию воспроизводимой базы; не закрывает известные P0/P1 приёмки отчёта и не подтверждает эмпирическую точность диагностики. Новую редакцию deployment pipeline, которую готовит отдельный агент, необходимо проверить отдельно.

## Что действительно реализовано

- Последний ответ, завершённый snapshot и оба задания — report и auth completion — сохраняются одной транзакцией. Повтор точного финального ответа возвращает PostgreSQL-результат без Redis, повторной оценки и повторного enqueue. Redis lock дополнен PostgreSQL row lock на переходе; конкурирующие финальные запросы покрыты HTTP-тестами.
- Resolver `/sessions/by-invite` восстанавливает конкретную принадлежащую приглашению попытку. Истечение срока после завершения не лишает доступа к сохранённому результату; terminal-приглашение не разрешает новую попытку или изменение ответа. Ошибки имеют стабильные `code/message/action`.
- Completion callback содержит время начала попытки. Брошенные auth claims возвращаются в очередь, свежие не отбираются; поздний ответ старого worker не перезаписывает новый claim. Доставка ограничена пятью попытками, автоматический бесконечный retry не заявляется.
- Подбор передаёт `target_b`, включая ноль, в content API до LIMIT. Ранняя остановка `classification_confident`: минимум 20 ответов, SE≤0,40, model category mass≥0,90, покрытие доступных L1-разделов; активный/обязательный критический Deep Scan блокирует её. Строгая ветка SE≤0,30 и максимум 42 сохранены. Завершение обхода разделов использует ту же политику; нижний класс не подменяет baseline coverage.
- Fisher information исправлена и проверена независимой конечной разностью. Этот helper не используется активным подбором, поэтому его исправлению не приписывается фактическое ускорение диагностики.
- Report schema 3 согласована между worker, public и staff API. Попытка целиком без ошибок больше не получает выдуманную слабую тему и коррекционный план из-за низкой накопленной alpha. Для попыток с ошибками рекомендации сохранены. Внутренний аудит различает measurement/prerequisite и причину остановки.
- Callback warnings и типичные HTTPX/Uvicorn access logs маскируют invite capability. Это не заявление о полном аудите всех reverse-proxy/Next.js логов.

## Что пока не реализовано и ограничивает приёмку

1. **P0 / N01–N02:** шесть содержательных находок T01–T06 не исправлены. Перед изменением задания необходимо сохранить исходное условие/варианты/ключ и связанные попытки: текущий live enrichment способен изменить контекст исторического отчёта при неизменном outcome. Это уже подтверждённый R03, а не новое требование.
2. **P0 / N02:** IRT-категория и пять бизнес-статусов отчёта используют разные шкалы; mixed-error попытка может получить ложную слабую тему после единственного верного ответа. Guard all-correct устраняет только полностью безошибочный сценарий; R01/R02 остаются открытыми.
3. **P1 / N03:** восстановление Deep Scan зависит от порядка `.all()` и теряет same-grade траектории. В P08 пять prerequisite вопросов и четыре фактических маршрута дали ноль цепочек. Это ошибка производного отчёта, не причина неправильной остановки на 30.
4. **P1 / N04–N05:** снятие баннера «Единая первопричина не подтверждена», снятие процента «надёжности», полная карта проверенных навыков, обоснование точного эквивалента класса, пересмотр когнитивных ярлыков/плана и полноценные UI-сценарии остаются в плане. Исправление header карточки не закрывает найденный overflow вкладок.
5. **P1 / N06:** LLM-интеграция уже существует, stage пока использует fallback из-за отсутствия ключей. До платного включения должны быть исправлены evidence и содержательные ограничения свободного заключения; подключение ключа само по себе R01–R03/R15 не исправляет. Generation failed/stale recovery UI требует отдельной приёмки.
6. **N10:** a/b/c банка пока стартовые; внешняя оценка учителя/независимого теста и калибровка не выполнены. «96,26%» является условной mass модели, «84% надёжности» — отдельной SE-эвристикой, «середина 10 класса» — другой неподтверждённой эвристикой. Их нельзя объявлять реальной точностью всего отчёта.

## Требования к текущей Git-фиксации

Сохранить runtime-код, meaningful tests и документацию вместе; release должен ссылаться на действительный Git commit, а не source bundle hash. Existing workflow запускался только от `main/develop`; push ветки CEO сам по себе не запускал его. В новой схеме CEO должен получать CI без неявной публикации production. Stage-релиз должен собираться из зафиксированного Git tree и проверять фактический revision/digest, runtime policy, миграции, readiness и откат. Приватные дампы, env/ключи, capability-коды и полные персональные отчёты в Git не включать.

`docs/diagnostic-lifecycle.md` описывает A2 и baseline SE≤0,30; дополнение про классификационную ветку P06 улучшит актуальность документации, но отсутствие этой заметки не является новым runtime-дефектом. Production-публикация и реализация N01–N12 текущим аудитом не выполнялись.
