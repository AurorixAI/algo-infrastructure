# ALGO — порядок разбора функций (решение владельца 27.10.2026)

Цель: каждая функция платформы проектируется и проверяется так, чтобы владелец не находил пробелы после «готово».
Правила-уроки — `LESSONS_LEARNED.md` (что нельзя повторять); этот файл — **как думать** (шаги, роли, выходы, ворота).
Навык для запуска: `.claude/skills/feature-analysis` (ведущий вызывает его перед ТЗ любой функции и для разбора уже существующих).

## 1. Когда разбор обязателен
* Новая функция или новая роль у существующей функции.
* Изменение денег, прав, расписания, посещаемости, экзаменов, отчётов.
* Любое замечание владельца «тут не продумано» → разбор всей функции, а не только места замечания.
* Плановый разбор существующих функций по `FEATURE_MAP.md` (по одной области за волну).
Мелкий текст/вёрстка без новой логики — только профиль UI (LESSONS §0).

## 2. Шаги (каждый шаг даёт письменный выход в документ разбора)
| # | Шаг | Выход |
|---|---|---|
| 1 | **Цель и люди**: зачем это центру; кто делает действие, кто видит результат (владелец, админ, преподаватель, заменяющий, ученик, родитель) | 3–5 строк |
| 2 | **Опись того, что уже есть** в коде у ЛЮБОЙ роли (эталон, правила, ограничения, тексты) — LESSONS №39 | таблица «правило → где есть → как будет» |
| 3 | **Жизненный цикл**: создать → изменить → отменить → вернуть → удалить/архив; что с прошлым и будущим | список состояний и переходов |
| 4 | **Матрица вариантов**: роли × действия × время (прошлое/сегодня/прошло время/будущее/далёкое) × состояние (архив, без преподавателя, замена, пауза, выходной, экзамен, оплата) × сбой (частичный отказ, двойное нажатие, одновременно двое, недоступный сервис, другой центр) | таблица «вариант → как сейчас → решение» |
| 5 | **Последствия**: деньги (долг, аванс, перерасчёт, зарплата, пакет), журналы и аудит, отчёты, уведомления, что видят ДРУГИЕ роли после действия, телефон | список влияний, у каждого — «проверено/изменить» |
| 6 | **Варианты решения** (LESSONS §0б): 2–3 способа, критерии, выбор с «почему не другие», что отложено и при каком факте вернуться | короткая таблица + решение |
| 7 | **Экран** (LESSONS §0): весь экран, существующие контейнеры, иерархия, минимум текста, по состоянию, один компонент для всех ролей | эскиз словами / список мест |
| 8 | **Проверки**: сценарии для тестов и для обхода stage (каждая строка матрицы шага 4 → тест или пункт обхода), инварианты | список сценариев |
| 9 | **Решения владельца**: только настоящие бизнес-выборы, с рекомендацией | 0–3 вопроса |

## 3. Роли агентов
| Роль | Модель | Что делает | Что возвращает |
|---|---|---|---|
| **Ведущий** (Opus) | — | заказывает разбор, принимает решения, пишет ТЗ, финальная приёмка | решение + ТЗ |
| **Аналитик** | Sonnet | шаги 1–5 и 8 по коду (только чтение) | документ разбора по шаблону |
| **Адвокат дьявола** | Sonnet | читает разбор и код, ищет НЕ рассмотренные варианты и последствия (новые строки матрицы) | список пропусков с доказательством |
| **Деньги/права** (по необходимости) | Sonnet | только последствия для денег, прав, данных | список рисков |
| **Исполнитель** | Sonnet | реализация по ТЗ | код + тесты + снимки |
| **R3** | Sonnet | ревью реализации против ТЗ и матрицы | находки |
Аналитик и адвокат — разные агенты (свежий взгляд). Ведущий сверяет оба выхода сам, не пересказывает.

## 4. Ворота (без выхода шага дальше не идём)
1. Разбор (шаги 1–9) → адвокат → ведущий закрыл пропуски → **ТЗ**.
2. ТЗ содержит матрицу и список сценариев → **реализация**.
3. R3 проверяет каждую строку матрицы → правки → проверка ведущего → общий e2e → **stage** (версия на сервере сверена) → обход по сценариям шага 8 → владелец → прод.
4. Нашли пробел на любом шаге → строка в матрицу + правило в LESSONS (если класс ошибки новый).

## 5. Документ разбора
`artifacts/analysis/<область>-<функция>.md` по шаблону навыка. Итоги и решения — строкой в ROADMAP.
