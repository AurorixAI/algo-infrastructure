# ALGO: Git → проверенный артефакт → stage

Перед commit/push или публикацией читать [поддерживаемый release runbook](../../../docs/releases/GIT_FIRST_STAGE.md). Он содержит команды, веточную маршрутизацию, manifest, подготовку чистого Git-источника, build/test и порядок отката. Не дублировать эти операции ad hoc скриптом из временного артефакта.

## Определить объём и происхождение

- ALGO состоит из отдельных Git-репозиториев. Проверить status/diff/remotes/ветку каждого затронутого репозитория; не считать workspace единым монорепозиторием. Не удалять чужие изменения и не использовать force/reset для удобства.
- Разрешение владельца на commit/push учитывать в текущей задаче без повторного запроса. Проверять имя ветки и реальную CI/CD-маршрутизацию. Push в рабочую CEO не равен публикации stage; слияние/продвижение в ветку auto-deploy — отдельное внешнее действие в разрешённом объёме.
- Рассмотреть tracked и нужные untracked файлы, миграции, тесты, runbooks и источники доказательств. Не коммитить `.env`, ключи, токены, приватные ответы, capability-коды, дампы учеников, сборки или локальные зависимости. Публичный итог редактировать до обезличенного доказательства; рабочие секреты остаются вне Git.
- Сверить опубликованный stage с исходниками по реальным файлам/образам/конфигурации. Старый overlay-релиз обозначать как overlay с проверенным составом: произвольный RELEASE_* label или совпадение одного метода не доказывает полный Git-источник. Исправление provenance требует сборки из конкретного Git-коммита и принятого образа.

## Проверяемый кандидат

Подготовить осмысленные коммиты по репозиториям; согласованные API и потребителей связать одним release manifest. Указать полный SHA каждого Git-репозитория, удалённое подтверждение push, тесты и версии схемы/контента. Не писать тестовые счётчики старого кандидата как проверку нового.

Следовать runbook: только чистый экспорт точного отправленного SHA, проверки этого источника, immutable image identity/digest, manifest и runtime-сверка после публикации. Секретную конфигурацию не включать в manifest; фиксировать безопасную идентичность/параметры среды без значений секретов. Банк/DB-правки не становятся сохранёнными в Git от одного push кода: сохранять reviewable спецификацию/миграцию и fingerprint плюс резервную копию вне Git.

Для stage-кандидата заранее подготовить предыдущие образы и manifest, совместимость схемы, резервную копию затрагиваемых данных и конкретную проверку возврата. Изменять только названные stage-сервисы. Не применять compose down или удаление volumes как этап публикации.

## Выпуск и откат

Если stage-релиз разрешён, выполнить предусмотренный runbook выпуск и сверить действующий артефакт, бизнес-сценарий, readiness и версии. Если разрешены только commit/push, завершить их, подготовить проверенный кандидат и запросить разрешение на конкретную публикацию последним шагом.

Разрешение на stage никогда не переносить на production; production выпускать только по явной авторизации. Название контейнера не доказывает среду: проверить compose project, URL/сеть и mount/config. В ALGO имя с `staging` использовалось для production; выбирать контур по runbook и фактам.

Возврат образа откатывает код, а не данные. У диагностического и content-сервисов migration runner может работать при старте: до перезапуска проверить поведение старого кода на текущей схеме. Не запускать destructive downgrade/restore и не пересчитывать реальные результаты без авторизованного плана. При несовместимости остановить зависимое продвижение и объяснить точную причину; продолжается подготовка безопасного варианта.

Закрыть работу доказательствами: ссылки на коммиты/ветки, release manifest, действующие image identities, выполненная приёмка, оставшиеся расхождения и состояние rollback. Возможность rollback по записанным образам и фактически проверенный rollback — разные утверждения.
